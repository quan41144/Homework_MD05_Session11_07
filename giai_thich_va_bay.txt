- Trong kiến trúc Microservices, các dịch vụ con (User, Product, Order, v.v.)
  thường chạy độc lập trên các cổng khác nhau (8081, 8082,...).
- Nếu để người dùng gọi trực tiếp tới các cổng này:
  + Client phải nhớ nhiều địa chỉ IP/Port khác nhau.
  + Dễ lộ cấu trúc hạ tầng nội bộ ra ngoài Internet.
  + Khó áp dụng tập trung các chính sách như SSL/TLS, xác thực (Auth), giới hạn tần suất (Rate Limit), bảo mật, hay logging.
- Nginx đóng vai trò API Gateway (Cổng giao tiếp tập trung):
  + Là điểm đón (Single Point of Entry) duy nhất tại cổng chuẩn 80/443.
  + Dựa vào URI (Path-based Routing) như `/user/` hoặc `/product/` để điều phối request về đúng dịch vụ backend.
## Bẫy:
Docker bỏ qua UFW FIREWALL
  Docker tự động can thiệp trực tiếp vào iptables của Linux. Nó tạo các quy tắc
  trong chuỗi PREROUTING và bảng NAT (DOCKER chain). Các gói tin đến cổng 8081
  từ card mạng ngoài (eth0) được chuyển tiếp thẳng vào container TRƯỚC KHI
  chuỗi INPUT của UFW được duyệt qua. Vì vậy, lệnh `ufw deny 8081` bị bỏ qua hoàn toàn.
- Giải pháp:
  Khi publish cổng container, chỉ liên kết với địa chỉ loopback nội bộ:
      docker run -d -p 127.0.0.1:8081:80 --name user_api nginx
      docker run -d -p 127.0.0.1:8082:80 --name product_api nginx
  Khi đó container chỉ lắng nghe trên giao diện mạng 127.0.0.1 (chỉ Nginx cùng host
  mới gọi được), bất kỳ ai từ bên ngoài Internet đều không thể kết nối tới cổng này.

Bẫy dấu / ở cuối proxy_pass
- Cấu hình 1 (CÓ dấu gạch chéo ở cuối):
      location /user/ {
          proxy_pass http://127.0.0.1:8081/;
      }
  -> Nginx sẽ bỏ tiền tố "/user/" trước khi gửi sang backend.

- Cấu hình 2 (KHÔNG CÓ dấu gạch chéo ở cuối):
      location /user/ {
          proxy_pass http://127.0.0.1:8081;
      }
  -> Nginx GIỮ NGUYÊN toàn bộ đường dẫn URI ban đầu.

Bẫy: tại sao phải có "proxy_intercept_errors on;"?
- Mặc định, nếu client gọi một URL không tồn tại tại Nginx, Nginx tự phát hiện 404 và hiển thị `custom_404.html`.
- Nhưng nếu client gọi tới route hợp lệ qua gateway, sau đó backend trả về HTTP 404, Nginx mặc định sẽ chuyển tiếp nguyên văn trang 404
  của backend cho người dùng.
- Thêm chỉ thị `proxy_intercept_errors on;` giúp Nginx "bắt" toàn bộ mã lỗi >= 300 từ backend
  để hiển thị thống nhất trang `custom_404.html` mà bạn đã tùy biến.

bẫy: chỉ thị "internal;" trong location lỗi
- Trong block cấu hình:
      location = /custom_404.html {
          root /usr/share/nginx/html;
          internal;
      }
